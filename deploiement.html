C8 Serveur partagé

Comprendre ce qui se passe

Votre projet tourne sur votre ordinateur. Pour le rendre accessible à tout le monde, on l'installe sur un serveur, qui reste allumé en permanence et possède une adresse web. Voici le chemin parcouru quand un visiteur tape l'adresse de votre site :

Visiteur  ->  Nginx  ->  Gunicorn  ->  Django / Wagtail  ->  base SQLite
  • Nginx reçoit les visiteurs. Il sert tout seul les fichiers statiques (CSS, JS, images) et passe le reste à Gunicorn.
  • Gunicorn fait tourner votre application Django en permanence, comme un service du serveur.
  • Django / Wagtail : votre projet, celui que vous connaissez.
  • SQLite : votre base de données, un simple fichier.

Le serveur est partagé par la promo : chacun a son espace et son adresse PRENOM.bdx-certif-cms.tech, et ne voit pas celui des autres. Votre fiche d'accès (adresse, identifiant, mot de passe) vous est remise séparément. Dans cette page, PRENOM désigne votre identifiant.

Ce qui change entre développement et production

C'est la question centrale de cette journée. Gardez ce tableau sous les yeux :

En local (développement)En ligne (production)
Serveurrunserver, un seul utilisateurNginx devant Gunicorn, plusieurs visiteurs en même temps
DEBUGTrue : les erreurs détaillées s'affichentFalse : jamais de détails d'erreur visibles
SECRET_KEYUne clé de développement dans le codeUne clé secrète, dans local.py, jamais sur GitHub
ALLOWED_HOSTS["*"] : tout est acceptéSeulement l'adresse du site
Fichiers statiquesServis par DjangoRassemblés par collectstatic, servis par Nginx
HTTPSNon (http://localhost)Oui, certificat gratuit
E-mailsAffichés dans le terminalConsole (minimum) ou vrai serveur d'envoi
Base de donnéesdb.sqlite3 sur votre postedb.sqlite3 sur le serveur
Pourquoi autant de différences ?

En développement, on veut voir les erreurs et aller vite. En production, des inconnus visitent le site : on cache les détails techniques, on protège les secrets et on chiffre les échanges.

1. Préparer son projet en local

Vérifier requirements.txt

Le serveur installera exactement ce que ce fichier demande. Il doit contenir au minimum :

Django>=6.1,<6.2
wagtail>=8.0,<8.1

Si votre projet utilise d'autres bibliothèques Python, elles doivent y figurer aussi.

Protéger vos secrets dans .gitignore

venv/
__pycache__/
*.pyc
.env
local.py
/media/
/static/
Piège

local.py contient les réglages secrets (clé secrète, identifiants de messagerie). Il ne doit jamais être envoyé sur GitHub : n'importe qui pourrait le lire.

Pousser le projet sur GitHub

git add .
git commit -m "Prêt pour la mise en production"
git push

Le serveur récupère votre code avec git clone : le dépôt doit donc être accessible, public le temps de la mise en production. Vérifiez qu'il ne contient aucun mot de passe ni aucune clé secrète.

2. Sur le serveur, étape par étape

Se connecter

Dans le terminal de votre ordinateur :

ssh PRENOM@bdx-certif-cms.tech
  • À la première connexion, le terminal demande de confirmer : tapez yes.
  • Tapez votre mot de passe. Rien ne s'affiche quand vous tapez, c'est normal.
  • Vous êtes connecté quand l'invite affiche PRENOM@srv...:~$.

Récupérer le code

git clone https://github.com/VOTRE-COMPTE/VOTRE-DEPOT.git app
Piège

Le dossier doit s'appeler app : c'est là que le serveur cherchera votre projet.

Créer l'environnement Python

python3 -m venv venv
source venv/bin/activate
pip install -r app/requirements.txt     # une à deux minutes

Même principe qu'en local : un environnement isolé, avec les versions demandées par votre projet.

Publier avec sudo publier

sudo publier

Cette commande affiche six étapes, avec une explication pour chacune. Lisez-les, elles sont le coeur de la mise en production :

ÉtapeCe qui se passe
1. Vérification du projetLe serveur contrôle que votre code est dans ~/app et que ~/venv existe.
2. Réglages de productionCréation du fichier settings/local.py : clé secrète, domaine autorisé, e-mail.
3. Base et fichiers statiquesmigrate met la base à jour, collectstatic rassemble les CSS et JS.
4. GunicornVotre application est lancée comme un service permanent.
5. NginxLe serveur web est configuré pour votre adresse.
6. HTTPSUn certificat gratuit est demandé automatiquement.
HTTPS déjà géré

Le HTTPS est géré par le serveur : vous n'avez rien à configurer. L'étape 6 demande votre certificat gratuit (Let's Encrypt) toute seule. À quoi ça sert : le HTTPS chiffre les échanges entre le visiteur et votre site (le cadenas du navigateur), évite l'avertissement « Non sécurisé » et protège les données saisies, par exemple dans le formulaire de contact ou à la connexion à l'administration.

Si une étape échoue, le message d'erreur s'affiche juste au-dessus : lisez-le, corrigez, puis relancez sudo publier. Vous pouvez la relancer autant de fois que nécessaire.

Vérifier en ligne

Ouvrez https://PRENOM.bdx-certif-cms.tech : le site doit s'afficher avec le cadenas. Testez aussi /admin/. En cas d'erreur, lisez les messages de votre site :

sudo mes-logs

Entrer dans l'administration

Pour vous connecter à /admin/, il faut un compte administrateur sur le serveur :

  • Si vous avez envoyé votre base (ou si elle est versionnée dans Git), vos comptes existent déjà : utilisez les mêmes identifiants qu'en local.
  • Si le mot de passe est oublié, ou si vous n'avez pas envoyé votre base, créez ou changez le compte sur le serveur :
cd ~/app
source ~/venv/bin/activate
export DJANGO_SETTINGS_MODULE=NOM_DU_PROJET.settings.production
python manage.py createsuperuser        # cree un nouveau compte administrateur
python manage.py changepassword NOM     # ou : change le mot de passe d'un compte existant
Pourquoi DJANGO_SETTINGS_MODULE ?

Par défaut, manage.py utilise les réglages de développement. Cette ligne lui dit d'utiliser ceux de production, ceux du serveur, avec la bonne base.

3. Envoyer sa base de données et ses médias

Votre base SQLite contient vos comptes administrateur et les contenus de votre site. Vos médias sont les images et documents envoyés depuis l'administration.

À regarder d'abord

Si db.sqlite3 et le dossier media sont versionnés dans Git, git clone les a déjà apportés : vous n'avez rien à faire. Sinon (c'est la bonne pratique de les ignorer), envoyez-les depuis votre ordinateur, pas depuis le serveur.

Placez-vous dans le dossier de votre projet (celui qui contient manage.py) :

scp db.sqlite3 PRENOM@bdx-certif-cms.tech:app/
scp -r media PRENOM@bdx-certif-cms.tech:app/

Le dossier app doit exister sur le serveur : faites cette étape après le git clone, puis relancez sudo publier. Le mot de passe est redemandé à chaque commande.

Plan B

Si la copie vous bloque : versionnez la base et les médias dans Git (retirez db.sqlite3 et /media/ du .gitignore, puis add, commit, push), et faites git pull dans le dossier app du serveur.

Piège

Si votre base est versionnée dans Git, un git pull peut remplacer celle du serveur et effacer les contenus créés en production. Choisissez un seul endroit où l'on modifie les contenus (l'ordinateur ou le serveur) et gardez-le.

Les photos et les médias en production

Il y a deux sortes d'images dans un projet Wagtail, et elles ne voyagent pas pareil :

Sorte d'imageOù elle estComment elle arrive en ligne
Image du site (logo, décor, dans static/)Dans le code du projetAvec git clone et sudo publier (collectstatic)
Photo ajoutée depuis l'administration (Images, ou un champ photo d'une page)Dans le dossier mediaAvec scp, ou en l'ajoutant directement depuis l'administration en ligne
  • Ajouter de nouvelles photos depuis l'administration en ligne fonctionne : elles sont enregistrées dans ~/app/media sur le serveur, et Nginx les sert. Chaque envoi peut faire jusqu'à 20 Mo.
  • Ces photos restent sur le serveur : elles ne sont pas dans Git, et ne sont pas sur votre ordinateur. Si vous ajoutez des photos en local plus tard, il faut les renvoyer avec scp.
Piège

Si une image ne s'affiche pas (absente ou erreur 403 « Forbidden ») : relancez sudo publier, qui remet les droits de lecture du dossier media. Nginx lit les images directement dans ce dossier, sans passer par Django : il doit donc avoir le droit de les lire, un fichier copié avec des droits trop restrictifs est refusé.

Corriger le nom d'hôte dans Wagtail

Une base copiée depuis votre ordinateur garde l'adresse localhost dans les réglages de site de Wagtail. Le site s'affiche quand même, mais les liens absolus et le plan du site utiliseront la mauvaise adresse. Dans l'administration : Réglages, puis Sites, puis modifier votre site :

  • nom d'hôte : PRENOM.bdx-certif-cms.tech
  • port : 443 (celui du HTTPS)
  • case « site par défaut » : cochée

4. Réglages de production et e-mails

Au premier sudo publier, un fichier NOM_DU_PROJET/settings/local.py est créé pour vous sur le serveur. Pour le modifier : nano app/NOM_DU_PROJET/settings/local.py (Ctrl+O puis Entrée pour enregistrer, Ctrl+X pour quitter), puis sudo publier.

RéglageÀ quoi il sert
SECRET_KEYClé secrète de Django, propre à votre site. Ne jamais la partager.
ALLOWED_HOSTSAdresses pour lesquelles Django accepte de répondre. Sinon : erreur 400.
CSRF_TRUSTED_ORIGINSAdresses autorisées à envoyer des formulaires (en https://).
SECURE_PROXY_SSL_HEADERIndique à Django que le HTTPS est géré en amont par Nginx.
EMAIL_BACKENDComment les e-mails sont envoyés (voir ci-dessous).

Le formulaire de contact en production

Rien à installer sur le serveur : l'extension de formulaires (wagtail.contrib.forms) est livrée avec Wagtail, et déclarée dans vos réglages. Voici ce qui voyage et comment :

  • Le code du formulaire (votre classe de page, son template) arrive avec git clone.
  • Les tables qui enregistrent les messages sont créées par migrate, lancé par sudo publier.
  • La page de contact et ses champs (nom, e-mail, message) sont du contenu de la base de données : ils arrivent avec votre db.sqlite3. Si vous n'avez pas envoyé votre base, la page n'existe pas en ligne : recréez-la dans l'administration, avec ses champs.
  • Les messages reçus apparaissent dans l'administration, menu Formulaires.

Faire partir les e-mails du formulaire de contact

Le formulaire de contact (extension de formulaires de Wagtail) enregistre le message dans l'administration, puis essaie d'envoyer un e-mail. Il faut régler l'envoi, en local comme en production. Trois niveaux :

NiveauOùRéglage
1. DéveloppementEn localEMAIL_BACKEND = "django.core.mail.backends.console.EmailBackend" : le message s'affiche dans le terminal (déjà dans dev.py).
2. Production minimaleSur le serveurLa même ligne dans local.py (ajoutée par sudo publier). Le message est enregistré dans l'administration, et le texte de l'e-mail est visible avec sudo mes-logs.
3. Envoi réelSur le serveurUn vrai serveur d'envoi (SMTP), voir ci-dessous.
Piège

Sans réglage d'envoi en production, le formulaire plante (erreur 500 à l'envoi), même si le message est bien enregistré. C'est pourquoi sudo publier ajoute le niveau 2 pour vous.

Pour cette mise en production, le niveau 2 suffit. Le niveau 3 se met dans local.py, jamais dans Git :

EMAIL_BACKEND = "django.core.mail.backends.smtp.EmailBackend"
EMAIL_HOST = "smtp.exemple.fr"
EMAIL_PORT = 587
EMAIL_USE_TLS = True
EMAIL_HOST_USER = "votre-identifiant"
EMAIL_HOST_PASSWORD = "votre-mot-de-passe-d-application"
DEFAULT_FROM_EMAIL = "contact@exemple.fr"

Pour tester : envoyez un message depuis votre formulaire en ligne, puis vérifiez qu'il apparaît dans l'administration (menu Formulaires) et, au niveau 2, dans sudo mes-logs.

5. Analyse de trafic : GoatCounter

Nous utilisons GoatCounter : gratuit, simple, sans base de données à gérer.

Pourquoi pas Google Analytics ?

Par manque de temps : il demande de créer un compte Google, de configurer la propriété, puis de mettre en place un bandeau de consentement aux cookies. GoatCounter donne un résultat exploitable en quelques minutes. Ce choix tient au temps disponible, pas à une limite de Google Analytics.

  1. Créez votre compte gratuit sur goatcounter.com et choisissez un code de site (par exemple votre prénom).
  2. Dans base.html (dossier templates de votre projet), ajoutez cette ligne juste avant la balise </body>, en remplaçant MONCODE :
<script data-goatcounter="https://MONCODE.goatcounter.com/count" async src="//gc.zgo.at/count.js"></script>
  1. En local : git add, git commit, git push.
  2. Sur le serveur : cd ~/app, git pull, sudo publier.
  3. Visitez votre site, rechargez le tableau de bord de GoatCounter : votre visite doit apparaître. Faites une capture d'écran pour le rapport.

Côté RGPD, GoatCounter se présente comme un outil qui ne dépose pas de cookies de suivi. Reformulez dans le rapport ce que vous constatez vous-même, en citant la page de l'outil, et reliez-le à votre travail sur la conformité RGPD.

7. Mettre à jour son site

Mettre à jour son code

  1. Modifier et tester en local.
  2. git push.
  3. Sur le serveur : cd ~/app, git pull, puis sudo publier.

Mettre à jour Wagtail, Django et les extensions

  1. Surveiller : lire les notes de version de Wagtail et de Django, en particulier les correctifs de sécurité.
  2. Sauvegarder la base avant toute mise à jour :
cp ~/app/db.sqlite3 ~/sauvegarde-$(date +%F).sqlite3
  1. Tester en local : modifier la plage de versions dans requirements.txt, mettre à jour, vérifier que le site fonctionne.
  2. Déployer : git push, puis sur le serveur git pull, pip install -r app/requirements.txt, sudo publier.
  3. Vérifier le site en ligne, et revenir à la sauvegarde en cas de problème.
À retenir

Une plage comme wagtail>=8.0,<8.1 reçoit automatiquement les correctifs, tout en bloquant les changements de version majeure : celles-ci se préparent, elles ne se font pas par surprise.
