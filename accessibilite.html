C7 Évaluation 2 — Cas pratique brief-accessibilite-projet-personnel.md

Rappel : pourquoi ce brief compte double

Le Cas pratique (Évaluation 2) dure 15 minutes de présentation suivies de 5 minutes de questions, sur l'optimisation référencement et accessibilité de votre application. Les critères insistent autant sur la justification de vos choix que sur leur implémentation : savoir expliquer pourquoi, pas seulement cocher la case.

1. Texte alternatif

Un alt manquant pousse un lecteur d'écran à annoncer le nom du fichier brut. Un alt bien rempli décrit ce que montre l'image, pas "image de" (redondant), et sert de texte de repli si l'image ne charge pas.

photo_alt = models.CharField(
    max_length=255, blank=True,
    help_text="Decrit la photo (SEO + accessibilite)",
)
{% image page.photo fill-800x600 alt=page.photo_alt %}
Rendez-le administrable

Comme le reste du contenu : un champ dédié rempli depuis l'admin par la même personne qui choisit la photo, pas un texte écrit en dur dans le template.

Cas particulier

Pour une image purement décorative (qui n'apporte aucune information), laissez le champ vide : alt="" est la bonne pratique, différent d'un alt absent.

2. Contraste des couleurs

Un texte dont la couleur est trop proche de son fond devient illisible pour une personne malvoyante, ou simplement en plein soleil. Privilégiez un texte foncé sur fond clair (ou l'inverse), en évitant les teintes proches. Lighthouse (point 8) vérifie précisément ce contraste.

3. Structure sémantique

Un lecteur d'écran s'appuie sur <header>, <nav>, <main>, <footer> comme repères de navigation. Avec des <div> génériques partout, ces repères disparaissent. Même logique pour les titres : <h1>, <h2>, <h3>... forment une table des matières que le lecteur d'écran peut parcourir.

  • Un seul <h1> par page.
  • Pas de saut de niveau (un <h1> suivi directement d'un <h4>).
  • base.html utilise les balises sémantiques, pas des <div> génériques.

4. Labels de formulaire

Sans lien explicite entre un <label> et son champ, un lecteur d'écran annonce juste "champ de saisie", sans dire lequel. L'association via for/id règle ça, avec un bonus pour tout le monde : cliquer sur le label déplace le focus dans le champ.

Bonne nouvelle

{{ form.as_p }} (vu dans le formulaire Wagtail Forms) génère déjà ce lien tout seul. À vérifier seulement si le formulaire a été personnalisé à la main, champ par champ.

5. Texte de lien explicite

Beaucoup de lecteurs d'écran permettent d'afficher la liste de tous les liens d'une page, sortis de leur contexte. Si plusieurs liens s'appellent tous "cliquez ici" ou "en savoir plus", impossible de savoir lequel mène où. Préférez un texte compréhensible seul : "Voir le cours Cardio Boost" plutôt que "en savoir plus".

6. Attention à ARIA

ARIA (role, aria-label, aria-hidden...) décrit un élément aux lecteurs d'écran, mais n'ajoute aucun comportement.

À éviter 
<div role="button" aria-label="Envoyer" onclick="submitForm()">Envoyer</div>
<!-- annonce "bouton", mais une div n'est pas focusable au clavier et ne reagit pas a Entree -->
La bonne solution 
<button type="submit">Envoyer</button>
<!-- fait tout ca nativement, sans aucun attribut ARIA -->

La règle à retenir : le HTML sémantique (point 3) suffit dans la grande majorité des cas. N'ajoutez un attribut aria-* que si vous savez précisément pourquoi la balise native ne suffit pas.

7. Focus clavier

Une personne qui navigue au clavier avance de lien en lien avec Tab. Le contour de focus (bleu, par défaut) est son seul repère.

À éviter 
a:focus, button:focus {
    outline: none;   /* supprime le contour, sans rien pour le remplacer */
}
La bonne solution 
a:focus, button:focus {
    outline: 2px solid #0071e3;   /* personnalise, mais toujours visible */
    outline-offset: 2px;
}

Comment tester : appuyez plusieurs fois sur Tab depuis le haut de la page, vérifiez que vous voyez toujours clairement où vous êtes.

8. Audit Lighthouse — l'étape la plus importante

Un outil ne remplace jamais une vraie attention portée aux points précédents, mais il repère objectivement ce qui aurait pu vous échapper, avec l'emplacement exact dans le code.

  1. Ouvrez la page dans Chrome, DevTools (Cmd+Option+I Mac, F12 Windows/Linux).
  2. Onglet Lighthouse (cliquez sur » si besoin).
  3. Décochez tout sauf Accessibilité.
  4. Mode "Navigation", appareil "Mobile" ou "Desktop".
  5. "Analyser la page" / "Generate report".

Le score compte moins que la liste détaillée des "Audits échoués" : vérifiez que chaque problème signalé correspond à quelque chose déjà traité dans les points 1 à 7, ou qu'il révèle un oubli. Faites tourner l'audit sur chaque page principale, pas seulement l'accueil.

Checklist avant l'oral

  • Toutes les images ont un alt pertinent, ou vide si décoratives (jamais absent)
  • Contraste texte/fond suffisant sur les pages principales
  • header/nav/main/footer utilisés, un seul h1 par page, pas de saut de niveau
  • Labels de formulaire correctement associés
  • Liens et boutons avec un texte compréhensible hors contexte
  • Aucun aria-* sans justification claire
  • Focus clavier toujours visible
  • Audit Lighthouse passé sur chaque page principale, problèmes corrigés
